## TRANSITION CONTRACT

### Canonical vendor lifecycle:
```
Consumer creates order (CONFIRMED + PAYMENT_PENDING)
  ↓ Payment captured (PAID)
Vendor accepts (Fulfilment.acceptedAt set — informational, no status change)
  ↓ PATCH /api/orders/[id]/fulfilment { status: PREPARING }
  ↓ (lazy-creates Fulfilment row if not exists)
Vendor marks ALMOST_READY
  ↓ PATCH /api/orders/[id]/fulfilment { status: ALMOST_READY }
Vendor marks READY_FOR_PICKUP
  ↓ PATCH /api/orders/[id]/fulfilment { status: READY_FOR_PICKUP }
  ↓ (also updates Order.status to READY_FOR_PICKUP via status route)
Pickup verification
  ↓ POST /api/orders/[id]/pickup/verify { otpId, code, qrToken }
  ↓ Sets Fulfilment.pickupVerifiedAt/By + Fulfilment.status = PICKED_UP
  ↓ Sets Order.status = PICKED_UP (via outbox event)
```

### Transition authorization:
| Transition | Route | Authorized actor | Ownership check |
|-----------|-------|------------------|----------------|
| Accept (acceptedAt) | POST /api/vendor/orders/[id]/accept | VENDOR_OWNER/ADMIN | Restaurant.ownerUserId === session.userId |
| PREPARING | PATCH /api/orders/[id]/fulfilment | VENDOR_OWNER/ADMIN | session check (route exists but NO vendor ownership check!) |
| ALMOST_READY | PATCH /api/orders/[id]/fulfilment | VENDOR_OWNER/ADMIN | session check (NO vendor ownership check!) |
| READY_FOR_PICKUP | PATCH /api/orders/[id]/fulfilment | VENDOR_OWNER/ADMIN | session check (NO vendor ownership check!) |
| PICKED_UP | POST /api/orders/[id]/pickup/verify | CONSUMER (own order)/VENDOR_OWNER/ADMIN | OTP + QR verification |
| CANCEL | PATCH /api/orders/[id]/status { status: CANCELLED } | CONSUMER (own order only)/VENDOR_OWNER/ADMIN | order.userId === session.userId |

### CRITICAL FINDING: Fulfilment route has NO vendor ownership check!

The `PATCH /api/orders/[id]/fulfilment` route only checks `getSessionUser()` and `session.role` (VENDOR_OWNER/ADMIN). It does NOT verify that the calling vendor owns the restaurant. **Vendor A can transition Vendor B's order status.** This is a security gap.

**Classification:** P0 — BLOCKS core security. Must be fixed before vendor lifecycle implementation.

## PAYMENT GATE

### Current behavior:
1. Order created with `status=CONFIRMED` and `pickupOtp` generated
2. Payment created with `status=PAYMENT_PENDING`
3. On payment capture (POST /api/payments): `Payment.status → CAPTURED`, `Order.status → PAID`
4. Vendor can accept/prepare orders regardless of payment status (no payment gate on fulfilment route)

### Payment states:
```
PAYMENT_PENDING → CAPTURE_PENDING → CAPTURED
CAPTURE_PENDING → FAILED
CAPTURED → REFUND_PENDING → REFUNDED | FAILED
(any) → FROZEN
```

### Issue: No payment gate on fulfilment transitions
- Vendor can start preparing an unpaid order (PAYMENT_PENDING)
- **Decision:** For demo mode (realPayments=false), this is acceptable — all payments are mock. For production, add `Payment.status === 'CAPTURED'` check before allowing PREPARING transition. **Classification: P2 (production readiness, not a blocker for dev).**

## PICKUP OTP CONTRACT

### Current implementation:
- **Generated:** On order creation — `pickupOtp` stored as plaintext on Order row (`default("000000")`)
- **OTP value:** 6-digit code, generated by `createOtp()` in order creation route
- **Storage:** `Order.pickupOtp` (plaintext String) + `Fulfilment.pickupOtp` (copied on lazy-create)
- **Expiry:** No explicit expiry on pickup OTP (OTP doesn't expire independently of order)
- **Attempt limit:** No attempt counter on pickup OTP verification
- **Verification:** POST /api/orders/[id]/pickup/verify with `{ otpId, code, qrToken }`
- **Attribution:** On success: `Fulfilment.pickupVerifiedAt` + `Fulfilment.pickupVerifiedBy` set
- **Single-use:** `pickupVerifiedAt` is checked — if already set, PICKED_UP is blocked (when flag ON)

### Security gaps:
1. **Plaintext OTP storage:** `Order.pickupOtp` stores the OTP as plaintext (not hashed)
2. **No attempt limit:** Wrong OTP can be tried unlimited times
3. **No OTP expiry:** OTP doesn't expire (only order cancellation invalidates it)
4. **pickupAttributionEnforcement flag OFF by default:** PICKED_UP can be set directly via PATCH /fulfilment without OTP verification

### Classification:
- Plaintext OTP: P2 (security hardening — not blocking dev)
- No attempt limit: P2 (brute force protection — add before production)
- No expiry: P3 (low risk — order lifecycle is short)
- Flag OFF by default: P3 (backward-compatible default — enable for production)

### Missing audit actions:

- ORDER_CANCELLED (dedicated audit for cancellation)

### All use `tx.auditLog.create` (NOT `auditWithTx` chained audit). This is a deviation from S4C hardened audit chain.

**Classification:** P1 — fulfilment transitions should use `auditWithTx` for chain integrity.

### Existing realtime events:

| order:created (socket) | Emitted via emitOrderUpdated | Same channels |
| order:updated (socket) | Emitted via emitOrderUpdated | Same channels |

### Fulfilment route does NOT emit realtime events directly
- It updates Fulfilment.status but does NOT call emitOrderUpdated or enqueueOutboxEvent for the fulfilment transition
- **Gap:** Consumer order tracking doesn't update when vendor transitions fulfilment status

**Classification:** P0 — consumer must see vendor transitions in realtime. This is the core of the order-to-pickup loop.

## CANCELLATION

### Current rules:
| State | Who can cancel | Result |
|-------|---------------|--------|
| CONFIRMED (before payment) | CONSUMER (own order) | status → CANCELLED |

### Missing: No refund trigger on cancellation after payment
- Cancellation sets `Order.status = CANCELLED` but does NOT trigger refund
