   112→## Part 3 — Bounded-Retry Proof
   113→
   114→Source: `src/lib/db.ts` (read in full, lines 1–176).
   115→
   116→### 3.1 MAX_RETRIES is finite
   117→
   118→```ts
   119→// src/lib/db.ts line 39
   120→const MAX_RETRIES = 5
   121→
   122→// src/lib/db.ts lines 95–101
   123→export async function withTransaction<T>(
   124→  fn: (tx: Prisma.TransactionClient) => Promise<T>,
   125→  options?: WithTransactionOptions,
   126→): Promise<T> {
   127→  const maxRetries = options?.maxRetries ?? MAX_RETRIES
   128→```
   129→
   130→- `MAX_RETRIES` is a module-level `const`, value `5`.
   131→- Callers MAY override via `options.maxRetries`, but no caller in the codebase passes that option (verified by Grep: `withTransaction(` is invoked with a single `async (tx) => {...}` argument in all 4 call sites).
   132→- The retry loop is bounded: `for (let attempt = 1; attempt <= maxRetries; attempt++)` (line 104). The loop cannot exceed `maxRetries`.
   133→
   134→### 3.2 After exhausting retries, a `TransactionConflictError` is thrown (not swallowed)
   135→
   136→```ts
   137→// src/lib/db.ts lines 110–129
   138→} catch (error) {
   139→  lastError = error
   140→  if (isRetryableConflict(error) && attempt < maxRetries) {
   141→    // Exponential backoff: 10ms, 20ms, 40ms...
   142→    const backoff = INITIAL_BACKOFF_MS * Math.pow(2, attempt - 1)
   143→    await sleep(backoff)
   144→    continue
   145→  }
   146→  // Not retryable, or out of retries
   147→  if (isRetryableConflict(error)) {
   148→    const code = (error as Prisma.PrismaClientKnownRequestError).code
   149→    throw new TransactionConflictError(
   150→      `Transaction conflicted after ${attempt} attempts (Prisma code ${code}). Retry the request.`,
   151→      code,
   152→      attempt,
   153→    )
   154→  }
   155→  // Non-conflict error — rethrow as-is
   156→  throw error
   157→}
   158→```
   159→
   160→- If `attempt < maxRetries` and the error is retryable → retry with backoff (continue).
   161→- If `attempt === maxRetries` and the error is still retryable → the first `if` is false (because `attempt < maxRetries` is false), so control falls to the second `if`: `isRetryableConflict(error)` is true → throws `TransactionConflictError`.
   162→- If the error is NOT a retryable conflict → falls through both `if`s and rethrows the original error as-is.
   163→
   164→There is no silent swallow path. The only `throw` paths are: `TransactionConflictError` (bounded) or the original non-retryable error (rethrown as-is).
   165→
   166→The unreachable tail at lines 132–137 is a defensive `throw new TransactionConflictError(... 'UNKNOWN' ...)` that satisfies the TypeScript return-type checker ("Function lacks ending return statement and return type does not include 'undefined'"). It cannot be reached because the `for` loop either returns from inside `try` or throws from inside `catch`.
   167→
   168→### 3.3 Retry re-runs the ENTIRE `fn` callback from the start
   169→
   170→```ts
   171→// src/lib/db.ts lines 104–109
   172→for (let attempt = 1; attempt <= maxRetries; attempt++) {
   173→  try {
   174→    return await db.$transaction(fn, {
   175→      timeout,
   176→      maxWait,
   177→    })
   178→  } catch (error) {
   179→    ...
   180→  }
   181→}
   182→```
   183→
   184→The retry passes the SAME `fn` reference to `db.$transaction`. Prisma's `$transaction(fn, options)` invokes `fn(tx)` fresh on each call — there is no checkpoint/resume mechanism. The body therefore re-executes from the first statement on every retry.
   185→
   186→This means:
   187→- For callers that start their body with `getCachedResponse(tx, idempotencyKey)` (callers #1 and #4): the cache check re-runs and short-circuits if another txn already committed the same key.
   188→- For callers that start with `findUnique(... { version })` followed by a conditional `updateMany WHERE version = expected` (callers #2 and #3): the re-read sees the updated version and the `updateMany` matches zero rows → handler returns 409.
   189→
   190→### 3.4 Worst-case behavior
   191→
   192→| Scenario | Behavior |
   193→|---|---|
   194→| Retryable conflict on attempt 1 | Backoff 50ms, retry. |
   195→| Retryable conflict on attempt 2 | Backoff 100ms, retry. |
   196→| Retryable conflict on attempt 3 | Backoff 200ms, retry. |
   197→| Retryable conflict on attempt 4 | Backoff 400ms, retry. |
   198→| Retryable conflict on attempt 5 (final) | Loop condition `attempt < maxRetries` is false (5 < 5 = false); control falls to the post-loop conflict handler which throws `TransactionConflictError(code, attempts=5)`. |
   199→| Caller catches `TransactionConflictError` | Returns HTTP 409 Conflict with a `CONFLICT` error code and a "Please retry" message (verified in all 4 callers' `catch (error)` blocks). |
   200→
   201→**Worst-case timing**: 50 + 100 + 200 + 400 = 750ms of cumulative backoff, plus up to 5 × `timeout` (30s) = 150s of worst-case txn wall-clock. In practice, SQLite busy-timeouts of 30s × 5 attempts is the absolute ceiling; on PostgreSQL the per-txn timeout is rarely hit because row-level locks don't queue like SQLite's single-writer lock.
   202→
   203→**Worst-case external observable effect**: a single HTTP 409 returned to the client with a "Please retry" message. No silent failure, no infinite loop, no unbounded retry storm.
   204→
   205→### 3.5 Verdict (Part 3)
   206→
   207→- MAX_RETRIES = 5 (finite). ✓
   208→- After exhaustion, `TransactionConflictError` is thrown (not swallowed). ✓
   209→- The `TransactionConflictError` is caught by every caller and translated to HTTP 409. ✓
   210→- Retry re-runs the entire `fn` from the start, so the `getCachedResponse` / optimistic-lock safety mechanism is re-evaluated on every retry. ✓
   211→- Worst case: bounded backoff (750ms cumulative) → HTTP 409 to client. ✓

   271→
   272→### 4.3 Real mode (`realPayments = true`, NOT authorized in 3a)
   273→
   274→In real mode (`src/lib/razorpay.ts` lines 122–129):
   275→
   276→```ts
   277→const instance = getRazorpayInstance()!
   278→const capture = await instance.payments.capture(razorpayPaymentId, amount, currency)
   279→```
   280→
   281→This fires a real HTTPS `POST /v1/payments/{id}/capture` to Razorpay's API. Razorpay's capture endpoint is **NOT idempotent** — calling it twice on the same `razorpayPaymentId` will:
   282→- First call: capture the authorized amount.
   283→- Second call: return an error (`The payment has already been captured`) OR — depending on the authorization state — capture a second time. Razorpay's behavior here is gateway-version-dependent and is treated as non-idempotent for safety.
   284→
   285→If `withTransaction` retries the body after `captureRazorpayPayment()` has already been called once:
   286→- The retry's `getCachedResponse(tx, idempotencyKey)` will only short-circuit IF the original txn committed its `IdempotencyKey` row. If the original txn failed AFTER `captureRazorpayPayment()` (line 155) but BEFORE `storeIdempotencyRecord` (line 268) — e.g., a P1008 socket timeout arrived after Razorpay responded 200 OK but before Prisma could write the Payment row — then:
   287→  - The original txn is rolled back (Payment, Order, LedgerEntry, AuditLog, Outbox, IdempotencyKey all rolled back).
   288→  - The capture call at Razorpay's gateway **was already fired and succeeded** — it is NOT rolled back.
   289→  - The retry re-runs the body from line 77. `getCachedResponse` returns `null` (the IdempotencyKey row was rolled back). The retry proceeds to call `captureRazorpayPayment()` again at line 155.
   290→  - Result: **double capture at the gateway**. The customer is charged twice.
   291→
   292→This is the classic "external side-effect inside a DB retry loop" hazard. It is precisely what Task `3a-arch-doc` documents as the `TRANSACTION_RETRY_INVARIANT` ("external gateway side-effect ≠ blind DB retry") in `/home/z/my-project/docs/TRANSACTION_RETRY_INVARIANT.md` (9 sections, ~14 KB).

   308→
   309→### 4.5 Mitigation path (already documented in Task `3a-arch-doc`)
   310→
   311→The architectural-invariant document (`/home/z/my-project/docs/TRANSACTION_RETRY_INVARIANT.md`) prescribes three acceptable configurations for when `realPayments` is authorized (Wave-3b or later):
   312→
   313→- **Option A** — Move `captureRazorpayPayment()` AFTER `withTransaction` commits (post-commit side-effect). The capture is no longer inside the retry loop.
   314→- **Option B** — Pre-generate a gateway-honored idempotency key (Razorpay supports an `X-Idempotency-Key` header on `POST /payments/{id}/capture` via the `notes[idempotency_key]` pattern). Pass it on every retry so Razorpay dedupes server-side.
   315→- **Option C (canonical)** — Outbox pattern. `enqueueOutboxEvent(tx, { eventType: 'PAYMENT_CAPTURE_REQUESTED', ... })` inside the txn (already wired via `src/lib/outbox.ts`). An outbox publisher worker (Sub-Wave 2b mini-service `outbox-publisher`) calls `captureRazorpayPayment()` exactly-once per outbox row, with its own retry + idempotency-key strategy.
