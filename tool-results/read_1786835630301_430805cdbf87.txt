    53→### 1.2 IdempotencyKey model (from `prisma/schema.prisma` lines 213–225)
    54→
    55→```prisma
    56→model IdempotencyKey {
    57→  id              String   @id @default(cuid())
    58→  key             String   @unique             // client-provided idempotency key
    59→  resourceType    String                       // "Order" | "Payment" | ...
    60→  resourceId      String                       // the created resource's id (for lookup)
    61→  responseStatus  Int                          // HTTP status code cached
    62→  responseBody    String                       // JSON-serialized response body
    63→  createdAt       DateTime @default(now())
    64→  expiresAt       DateTime                     // TTL (default 24h)
    65→
    66→  @@index([resourceType, resourceId])
    67→}
    68→```
    69→
    70→**Key fields confirmed:**
    71→- `key` is `@unique` → PostgreSQL emits P2002 (unique-constraint violation) on a duplicate insert, which `withTransaction` (P2002-retryable) catches and re-runs from the start, where `getCachedResponse` finds the now-committed row → short-circuit.
    72→- `resourceType` + `resourceId` form a lookup index (used for cross-referencing — e.g., "which Order does this key belong to?").
    73→- `responseBody` stores the FULL JSON response body (status + body both cached).
    74→- `expiresAt` is set 24 hours in the future from creation. `getCachedResponse` checks `record.expiresAt.getTime() < Date.now()` and returns `null` on expiry (treats as "not found", allowing a fresh creation under the same key — **a known TTL caveat, see §3.6**).

   124→### 1.6 Lifecycle / state transition isolation
   125→
   126→The Order PATCH endpoint (`src/app/api/orders/[id]/status/route.ts`, read in full) uses a **completely different** concurrency mechanism:
   127→- **No `Idempotency-Key` header accepted.** Reads `status` + `actorRole` from body only.
   128→- Uses optimistic-lock `updateMany({ where: { id, version: order.version }, data: {...} })` and checks `updated.count === 0` → returns 409 "Order was modified by another request. Please refresh and retry."
   129→
   130→**This means state transitions cannot be idempotent-replayed** — the version field bumps on every successful transition, so a stale-state retry will always hit `count: 0` and 409. The boundary between idempotency (POST) and optimistic-lock (PATCH) is **clean**. No risk of "idempotent-replayed state transition."
   131→
   132→### 1.7 Outbox event atomicity (P0-24)
   133→
   134→`enqueueOutboxEvent(tx, {...})` (lines 275–287 in `orders/route.ts`) writes an `Outbox` row inside the same transaction. The Outbox row is committed atomically with the Order + OrderItems + AuditLog + IdempotencyKey. If any one fails, all roll back. **This is proven by Wave-2 2a rollback-injection evidence** (workflow 31869987403, `atomicRollback: true`).

   183→
   184→### 3.2 Retry after response loss
   185→
   186→- **Current state:** ❌ **NOT specifically proven for Order POST**. The mechanism IS implemented (the `getCachedResponse(tx, key)` check at the start of the txn body returns the cached response on retry), but no test has simulated the "server commits + response lost (network failure) + client retries with same key" scenario for Order POST.
   187→- **Risk if not closed:** MEDIUM. The client retries with the same `Idempotency-Key` and expects the cached response. If the cached response is somehow corrupted or the `IdempotencyKey.responseBody` was not committed (e.g., a partial-commit bug), the retry would create a duplicate order — a direct violation of I-02 Order Integrity.
   188→- **Required evidence:** Scenario: (1) intercept the response after the server commits (mock the network-layer response-send failure), (2) verify the Order row is in the DB, (3) client retries with the same `Idempotency-Key` + same body, (4) server returns the **same orderId** with HTTP 200 (cached response), (5) DB still has exactly 1 Order (not 2). The test must run on PostgreSQL.
   189→
   190→### 3.3 Materially different request + same key
   191→
   192→- **Current state:** ❌ **NOT proven for Order POST.** Wave-3a 3a-E3 proved this for PAYMENT (same key + different orderId → cached response returned, no second capture). For Order POST, the equivalent scenario is: client sends key=K + body B1 (restaurant=R1, items=[m1]) → server creates Order O1 and caches the response. Later, client (buggily) sends key=K + body B2 (restaurant=R2, items=[m2]) → server should return cached response (B1's orderId) OR return a 409/422 conflict. Currently the code returns the cached response (B1's) because `getCachedResponse` does not compare the request body to the cached request body — it just returns the cached response.
   193→- **Decision needed:** Should the second request (materially different body, same key) return:
   194→  - **Option A (current behavior):** Cached response from the first request. The second request is silently treated as a retry. This is the **Stripe/Razorpay convention** but can mask client bugs (e.g., a frontend bug reusing a key across different orders).
   195→  - **Option B (proposed):** Compute a hash of the request body, store it alongside the cached response, and on the second request, if the body hash differs, return HTTP 422 `IDEMPOTENCY_KEY_REUSE` with a clear message. This is the **GitHub/HTTP WG convention** (RFC draft: idempotency-key semantics).
   196→- **Risk if not closed:** LOW-MEDIUM. The current Option A behavior is "safe by correctness" (no duplicate order created), but "unsafe by client-bug-masking" (a buggy client could think its second (different) order was placed, when in fact the first (different) order's response was returned).
   197→- **Required evidence:** A test that sends the same `Idempotency-Key` with TWO materially different request bodies (different `restaurantId` and/or different `items[]`) and asserts the system's behavior matches the **decision** (Option A or Option B). Whichever option is chosen, the test must prove it. The decision must be documented in this Gate Review (see §5).
   198→

   205→### 3.5 Transaction rollback interaction
   206→
   207→- **Current state:** 🟡 **PARTIALLY proven.** Wave-2 2a rollback-injection test proved the `withTransaction` rollback guarantee — but using a synthetic `/api/test/rollback-injection` endpoint, NOT the real `/api/orders` route. The 2a evidence verified `orderExists: false, outboxExists: false, atomicRollback: true` after deliberate mid-txn failure. Wave-3a 3a-E1 proved the same for `/api/payments`. **The real `/api/orders` route has NOT had its rollback interaction empirically tested.**
   208→- **Risk if not closed:** MEDIUM. The Order POST route writes 5 entities inside the txn (MenuItem decrement, Order, OrderItem, AuditLog, IdempotencyKey, Outbox). If the txn fails mid-way (e.g., MenuItem sold out, restaurant suspended, DB connection lost), the IdempotencyKey must NOT be stored — otherwise the client's retry with the same key would receive the cached (failed) response and never be able to retry successfully. This is the **phantom-block prevention** guarantee.
   209→- **Required evidence:** Scenario: (1) Set up a menu item with `availableCount=0` (or a suspended restaurant), (2) POST /api/orders with `Idempotency-Key: K` + body requesting that item, (3) server returns 400/409 (item unavailable / restaurant suspended), (4) DB verification: 0 Order rows, **0 IdempotencyKey rows** (the key was NOT stored because the txn rolled back), (5) Client retries with the same key K + a DIFFERENT body (valid item) → server creates the order successfully (the key was NOT phantom-blocked). The test must prove `idempotencyRecordCount: 0` after the failed attempt.

   211→### 3.6 Lifecycle / state transition
   212→
   213→- **Current state:** ✅ **IMPLEMENTED + STRUCTURALLY PROVEN.** Reading the code:
   214→  - `POST /api/orders` accepts `Idempotency-Key` and uses the `IdempotencyKey` table for dedup.
   215→  - `PATCH /api/orders/[id]/status` does **NOT** accept `Idempotency-Key` (verified by reading `src/app/api/orders/[id]/status/route.ts` — the request body schema is `statusUpdateBodySchema = z.object({ status, actorRole? })`, no header extracted).
   216→  - `PATCH /api/orders/[id]/status` uses **optimistic-lock `updateMany({ where: { id, version: order.version } })`** with `count === 0` → 409. The version field bumps on every successful transition, so a stale-state retry will always 409.
   217→  - Therefore: **state transitions cannot be idempotent-replayed.** The boundary between idempotency (POST) and optimistic-lock (PATCH) is clean.
   218→- **Risk if not closed:** LOW. The current design is correct by construction. No additional evidence is strictly required, but a negative-test scenario (sending an `Idempotency-Key` header on PATCH and confirming it is ignored — i.e., the second PATCH with the same key still applies if the version matches) would strengthen the formal proof.
   219→- **Required evidence:** Scenario: (1) PATCH /api/orders/[id]/status with `Idempotency-Key: K1` (CONFIRMED → PREPARING) → 200, version bumps. (2) PATCH /api/orders/[id]/status with the SAME `Idempotency-Key: K1` (PREPARING → ALMOST_READY) → 200 (different transition succeeds). (3) Confirm no `IdempotencyKey` rows exist for PATCH operations (`SELECT * FROM IdempotencyKey WHERE resourceType = 'OrderStatus'` returns 0 rows).
   220→
   221→### 3.7 Conflict semantics
   222→
   223→- **Current state:** 🟡 **IMPLEMENTED, but client-actionability 409 message unclear.** The 409 response from `POST /api/orders` (line 319) is:
   224→  ```json
   225→  {
   226→    "error": {
   227→      "code": "CONFLICT",
   228→      "message": "Order could not be processed due to a concurrent modification. Please retry.",
   229→      "traceId": "..."
   230→    }
   231→  }
   232→  ```
   233→  This message does **not** distinguish between:
   234→  - **Retry-with-same-key scenarios:** P2002 (another concurrent txn committed the same key), P1008 (socket timeout — retry will find cached response if first txn committed), P2024 (pool timeout — same as P1008). The client SHOULD retry with the same `Idempotency-Key`.
   235→  - **Give-up scenarios:** P2034 (deadlock — retry with same key MIGHT work, but if the underlying business state changed, e.g., item sold out, a retry will return 400 not 409), P2036 (tx timeout — usually retryable, but may indicate persistent DB issues).
   236→  - **Business-rule conflicts:** A 409 returned from `tx.menuItem.updateMany` returning `count: 0` (item sold out) — the message says "Item 'X' was sold out by another order. Please retry." — but this is a separate 409 path (lines 170–178) with a different message, NOT the `TransactionConflictError` path. Still, the client may not understand whether to retry with the same key (cached response will be returned) or refresh inventory and place a new order with a new key.
   237→- **Risk if not closed:** LOW. The client experience today is "retry the request" which is correct for P2002/P1008/P2024 (idempotency-keyed retries will find the cached response). But if the client retries with a NEW `Idempotency-Key` after a 409, it will create a duplicate order — a subtle client-bug risk.
   238→- **Required evidence:** A test that sends 2 concurrent POST /api/orders with the same `Idempotency-Key` and inspects the 409 response of the loser to confirm it includes actionable guidance (e.g., `details: { retryStrategy: 'same-key' }`). Optionally improve the error message in the 3b implementation (see §5 code-change candidates).

   254→## 4. Failure / Concurrency Scenarios
   255→
   256→### 4.1 withTransaction retry impact on Order POST
   257→
   258→Source: `src/lib/db.ts` (read in full, lines 1–176) and `src/app/api/orders/route.ts` (read in full, lines 1–327).
   259→
   260→**Is the Order POST route retry-safe?** **YES** — confirmed by reading the entire `withTransaction(async (tx) => {...})` body (lines 102–290 of `orders/route.ts`):
   261→
   262→| Code site | Operation | External side-effect? | P2002 target? |
   263→|-----------|-----------|----------------------|----------------|
   264→| Line 106 | `getCachedResponse(tx, idempotencyKey)` | No (pure DB read) | No (read) |
   265→| Line 121 | `tx.menuItem.findMany(...)` | No | No (read) |
   266→| Line 159 | `tx.menuItem.updateMany(...)` (conditional) | No | No (`MenuItem.id` is server-generated; the WHERE clause filters on `version` so count=0 is a normal race-loser signal, not a P2002) |
   267→| Line 181 | `tx.restaurant.findUnique(...)` | No | No (read) |
   268→| Line 195 | `tx.order.create(...)` | No | No (`Order.id` is server-generated cuid; no unique constraint on user-supplied fields that would P2002) |
   269→| Line 220 | `tx.auditLog.create(...)` | No | No (`AuditLog.id` is server-generated) |
   270→| Line 258 | `storeIdempotencyRecord(tx, ...)` (conditional) | No | **YES** — `IdempotencyKey.key` is `@unique`. This is the ONLY P2002 target in the body. |
   271→| Line 275 | `enqueueOutboxEvent(tx, ...)` | No | No (`Outbox.id` and `Outbox.eventId` are server-generated; `eventId` uses `crypto.randomUUID()` so collision is astronomically unlikely) |
   272→
   273→**Conclusion:** The only P2002 surface in the Order POST body is `storeIdempotencyRecord` on the `IdempotencyKey.key` unique constraint. When a retry occurs (P2002, P1008, P2024, P2034, P2036), the body re-runs from line 106 (`getCachedResponse`), which finds the now-committed `IdempotencyKey` row and short-circuits. No duplicate Order, no duplicate OrderItem, no duplicate AuditLog, no duplicate Outbox event.
   274→
   275→**No external side-effects inside the txn body.** The `emitOrderCreated({...})` call (line 303) is **outside** the `withTransaction` block (after the result is returned), so it is NOT retried. This conforms to Option A of the `TRANSACTION_RETRY_INVARIANT` (post-commit side-effect).
   276→
   277→**Could a retry create a duplicate order?** **NO** — the `getCachedResponse` short-circuit at line 106 prevents the body from reaching `tx.order.create` (line 195) on retry.
   278→
   279→**Is the retry bounded?** **YES** — `MAX_RETRIES = 5` (const, line 39 of `db.ts`). No caller overrides it (verified by Grep — all 4 callers invoke `withTransaction(async (tx) => {...})` with a single argument). After exhaustion, `TransactionConflictError` is thrown (not swallowed). The Order POST catch block (lines 313–326) translates this to HTTP 409.
   280→
   281→**Worst-case client experience:** 5 retries × exponential backoff (50ms + 100ms + 200ms + 400ms = 750ms cumulative) + final HTTP 409. Total wall-clock ≤ 5 × 30s txn timeout = 150s ceiling (rarely hit on PostgreSQL because row-level locks don't queue like SQLite's single-writer lock).
   282→
   283→### 4.2 P2002 race scenario (concurrent same-key POST /api/orders)
   284→
   285→Two concurrent requests A and B with the same `Idempotency-Key: K`:
   286→
   287→| Time | Request A | Request B | DB state |
   288→|------|-----------|-----------|----------|
   289→| t0 | Begin txn | Begin txn | (empty) |
   290→| t1 | `getCachedResponse(K)` → null | `getCachedResponse(K)` → null | (no key yet) |
   291→| t2 | MenuItem read + decrement | MenuItem read + decrement (may 409 on `version` if A committed first, OR succeed if version still matches — but P0-25 Case A handles this) | (depends) |
   292→| t3 | `tx.order.create(...)` → O1 | (proceeds to `tx.order.create(...)` → O2 if version matched) | O1 created |
   293→| t4 | `storeIdempotencyRecord(K, 'Order', O1, 200, body)` → SUCCESS | `storeIdempotencyRecord(K, ...)` → **P2002** (key already exists from A's commit, IF A committed between t4-A and t4-B) | IdempotencyKey(K) committed |
   294→| t5 | `enqueueOutboxEvent(...)` → E1 | (caught by `isRetryableConflict` → backoff 50ms → retry) | Outbox E1 committed |
   295→| t6 | Commit | Retry begins: `getCachedResponse(K)` → **cache hit** (returns A's cached response body) | (no change) |
   296→| t7 | Return 200 with O1 | Short-circuit, return cached 200 with O1 | (no change) |
   297→
   298→**Net result:** Exactly 1 Order (O1), exactly 1 IdempotencyKey, exactly 1 Outbox event. Both A and B receive HTTP 200 with the same orderId (O1). This is the **canonical idempotent-create pattern** and is structurally identical to the Payment scenario proven in 3a-PG-E1.
   299→
   300→### 4.3 Phantom-block scenario (failed txn + retry with same key)
   301→
   302→Request A fails mid-txn (e.g., MenuItem sold out):
   303→
   304→| Time | Request A | DB state |
   305→|------|-----------|----------|
   306→| t0 | Begin txn | (empty) |
   307→| t1 | `getCachedResponse(K)` → null | (no key) |
   308→| t2 | `tx.menuItem.updateMany` returns `count: 0` (item sold out) | (no change) |
   309→| t3 | Return `{ type: 'error', status: 409, body: { error: 'CONFLICT', message: '...sold out...' } }` | (no IdempotencyKey written) |
   310→| t4 | Transaction rolls back (no commit) | (no Order, no IdempotencyKey, no Outbox) |
   311→| t5 | Client receives 409 with sold-out message | (clean) |
   312→| t6 | Client retries with same `Idempotency-Key: K` + DIFFERENT body (valid item) | (clean) |
   313→| t7 | `getCachedResponse(K)` → null (key was rolled back) → proceeds with new order creation | (new order O2 created, key K stored) |
   314→
   315→**Net result:** Phantom-block is prevented because the `IdempotencyKey` row is committed atomically with the Order. If the txn fails, the key is NOT stored. The client can retry with the same key and place a different order successfully.
   316→
   317→**However**, the current 409 message ("Order could not be processed due to a concurrent modification. Please retry.") is **ambiguous** — the client cannot tell whether:
   318→- It should retry with the SAME `Idempotency-Key` (the cached response will be returned if the original txn committed), OR
   319→- It should refresh the inventory and place a NEW order with a NEW key (because the original txn failed on a business rule, not a conflict).
   320→
   321→This is the **conflict-semantics gap** (§3.7).
   322→
   323→### 4.4 Concurrent inventory race (P0-25 Case A) interaction
   324→
   325→The `tx.menuItem.updateMany({ where: { id, availableCount: { gte: qty }, version } })` call (lines 159–169) is the inventory-race guard. If two concurrent orders race for the last item:
   326→- A wins: `updateMany` returns `count: 1`, proceeds to create order.
   327→- B loses: `updateMany` returns `count: 0` (because either `availableCount` dropped below qty OR `version` changed), returns 409 "Item 'X' was sold out by another order. Please retry."
   328→
   329→This is the **same `version`-based optimistic-lock pattern** used by the Order PATCH route (P0-25 Case B). It is **proven by Wave-1 Track B Case A evidence**.
   330→
   331→### 4.5 Outbox event atomicity interaction
   332→
   333→The `enqueueOutboxEvent(tx, { eventType: 'ORDER_CREATED', ... })` call (lines 275–287) writes an Outbox row inside the same transaction. If the Order POST transaction commits, the Outbox row is committed atomically. If it rolls back, the Outbox row is rolled back. This is the **canonical transactional outbox pattern** and is proven by Wave-2 2a rollback-injection evidence.
   334→
   335→The Outbox publisher (Sub-Wave 2b) later picks up the PENDING row, claims it atomically, publishes via Socket.io, and marks it PUBLISHED. **The publisher is decoupled from the Order POST route** — a publisher failure does NOT affect the Order POST transaction. This is the correct architectural separation.

   420→## 7. Risk / Rollback Analysis
   421→
   422→### 7.1 Risk level: **LOW** (for evidence-only 3b) / **MEDIUM** (if C1 or C2 are implemented)
   423→
   424→**Justification:**
   425→
   426→- **LOW risk (evidence-only 3b):** The 3b implementation can be scoped to ONLY the evidence scenarios (§6) + the evidence infrastructure (C5 + C6). No production code paths change. No schema changes. No API contract changes. The Order POST route is unchanged. Risk = "evidence test runs against staging, no production impact." This is the **same risk profile as 3a-evidence**, which the Orchestrator already accepted.
   427→
   428→- **MEDIUM risk (if C2 implemented):** C2 changes the 409 response shape (adds `details.retryStrategy` field). This is an additive, backward-compatible change — existing clients that don't read `details.retryStrategy` continue to work. But the change touches the Order POST critical path. Risk = "a client may have hardcoded assumptions about the 409 response shape that break with the new field." Mitigation: add the field only when the `CONFLICT` is from `TransactionConflictError` (not from business-rule 409s like sold-out). The sold-out 409 keeps its current shape.
   429→
   430→- **MEDIUM risk (if C1 implemented):** C1 adds a `requestHash` column + 422 `IDEMPOTENCY_KEY_REUSE` error. This changes the API contract (a same-key + different-body request now returns 422 instead of 200). Risk = "a client that legitimately retries with the same key but a slightly-different body (e.g., whitespace normalization, ordering) gets a 422 and breaks." Mitigation: hash normalization (e.g., JSON canonicalization) + make the column nullable (existing rows have null → no hash check). **C1 is NOT recommended for 3b** — defer to Wave-3c or later where the contract change can be trialed with a feature flag.
