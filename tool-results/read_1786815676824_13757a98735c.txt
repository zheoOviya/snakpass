   251→
   252→**Result:**
   253→- All 5 requests returned `status=200` (the retry mechanism handled concurrent contention — losers found the cached response)
   254→- `uniquePaymentIds: 1` (all 5 responses returned the SAME paymentId)
   255→- `successCount: 5`, `errorCount: 0`
   256→- DB verification: exactly 1 Payment (CAPTURED), 2 LedgerEntries (Dr+Cr), 1 Outbox, 1 IdempotencyRecord
   257→- `exactlyOneCapture: true`
   258→
   259→**Proof:** From 5 simultaneous concurrent requests with the same idempotency key:
   260→- Exactly 1 Payment was created (not 0, not 5)
   261→- Exactly 1 ledger pair (Dr + Cr)
   262→- Exactly 1 outbox event
   263→- Exactly 1 idempotency record

   265→
   266→**Note on database engine:** This test was run on local SQLite (staging/production use PostgreSQL).
   267→SQLite uses a database-level write lock; PostgreSQL uses row-level locks. The INVARIANT
   268→(exactly 1 Payment) holds on both engines because:
   269→1. The `IdempotencyKey.key` unique constraint prevents duplicate keys
   270→2. The `Payment.orderId` unique constraint prevents duplicate payments for the same order
   271→3. The `getCachedResponse` check at the start of the transaction returns the cached response on retry
   272→On PostgreSQL, the concurrent losers would get P2002 (unique constraint violation) immediately
   273→(rather than queueing), and the retry would find the cached response faster.
   274→The `withTransaction` retry logic was enhanced to handle P2002 + P1008 (socket timeout) for
   275→this concurrent-idempotency scenario.

   335→#### Critical Audit Caveat (Orchestrator-noted)
   336→
   337→> **3a evidence proves the application-level idempotency/atomicity invariants,
   338→> but the concurrency evidence is not yet PostgreSQL-native evidence.**
   339→
   340→The 4 evidence tests were executed against local **SQLite** (no local
   341→PostgreSQL available in the sandbox — no sudo, no Docker, no `initdb`).
   342→SQLite and PostgreSQL differ in concurrency model:
   343→
   344→| Engine | Concurrency Model | Effect on Test 4 (concurrent) |
   345→|--------|-------------------|-------------------------------|
   346→| SQLite | Database-level write lock (BEGIN IMMEDIATE) | Concurrent transactions queue for the write lock; losers get P1008 (socket timeout) and retry → cached response |
   347→| PostgreSQL | Row-level locks + MVCC | Concurrent transactions proceed in parallel; the loser hits P2002 (unique constraint violation on `IdempotencyKey.key`) immediately and retries → cached response |
   348→
   349→**The INVARIANT (exactly 1 Payment from N concurrent requests) holds on BOTH
   350→engines** because:
   351→1. `IdempotencyKey.key` UNIQUE constraint prevents duplicate keys
   352→2. `Payment.orderId` UNIQUE constraint prevents duplicate payments for the same order
   353→3. `getCachedResponse` check at the start of the transaction returns cached response on retry
   354→4. `withTransaction` retry logic (P2002/P1008/P2034/P2036/P2024) handles both engines' conflict signals
   355→
   356→**However**, the Orchestrator correctly notes that calling this
   357→"production-grade PostgreSQL concurrency proof" is premature without
   358→running the test against actual PostgreSQL. The staging PostgreSQL
   359→concurrent-idempotency test remains an open evidence gap.
