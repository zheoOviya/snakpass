   623→### 8.5 Does C1 interact with `withTransaction` retry? (explicit answer)
   624→
   625→**YES, but safely.** The hash check happens INSIDE the txn body (in `getCachedResponse`, which is the FIRST call inside `withTransaction`). On retry:
   626→
   627→1. `withTransaction` catches a retryable conflict (P2002/P1008/P2024/P2034/P2036).
   628→2. Backoff + retry — the SAME `fn` callback is invoked fresh.
   629→3. `getCachedResponse(tx, key, incomingRequestHash)` re-runs.
   630→4. Reads the same `IdempotencyKey` row (either committed by the prior attempt, or by a sibling transaction).
   631→5. Hash check: `incomingRequestHash` (computed once outside the txn — same value on every retry) compared with `record.requestHash` (deterministic — same value on every read).
   632→6. **If hash matches:** cached response returned → short-circuit (same as today).
   633→7. **If hash mismatches:** `IdempotencyKeyReuseError` thrown → propagates out of `withTransaction` (NOT a retryable conflict — `isRetryableConflict` returns `false` for non-Prisma errors). Route handler catches it → HTTP 422.
   634→
   635→**Is this correct?** YES. If the hash mismatches on retry, it will mismatch on every retry (the stored hash is committed; the incoming hash is fixed). Retrying would be wasteful. The 422 is the correct terminal behavior — the client must generate a new `Idempotency-Key`.
   636→
   637→**Edge case:** What if the FIRST attempt's txn committed (stored hash = H1), but the client's retry sends a DIFFERENT body (hash = H2)? The hash check correctly returns 422. The client must generate a new key. This is the intended Option B behavior — no bug.
   638→
   639→**Edge case:** What if the FIRST attempt's txn rolled back (no row stored), and the retry sends the SAME body (hash = H1)? `getCachedResponse` returns `null` (no row) → proceeds with business write → stores row with `requestHash = H1`. No 422. Correct behavior — this is the 3b-E5 phantom-block scenario, preserved.
