   260→
   261→```yaml

   269→### 6.1 Phase timeline
   270→
   271→| Phase | Step name | Captures |
   272→|---|---|---|
   273→| A | `Record rollback start (T0)` | `t0_iso`, `t0_epoch` |
   274→| B | `Promote target deployment to production` | `t1_iso`, `t1_epoch`, `prod_url`, `promotion_target` |
   275→| C | `Verify post-rollback health` | `t2_iso`, `t2_epoch`, `rollback-smoke-results.json` |

   279→### 6.2 ≤10-minute assertion
   280→
   281→```bash
   282→BUDGET_SECS=600
   283→if [ "$TOTAL_SECS" -gt "$BUDGET_SECS" ]; then
   284→  echo "::error::Rollback exceeded 10-minute budget (took ${TOTAL_SECS}s)."
   285→  exit 1
   286→fi
   287→```
   288→
   289→`TOTAL_SECS = t2_epoch - t0_epoch` (T0 → T2, end-to-end including the 20-second edge propagation wait). Exit non-zero if exceeded → workflow fails → operator alerted.

   292→
   293→`evidence/` bundle contents:
   294→- `rollback-evidence.json` — composed doc with target, reason, actor, prod_url, timing, smoke results.
   295→- `timing.env` — flat key=value pairs (machine-parseable).
   296→- `rollback-smoke-results.json` — raw smoke-test output (if health check ran).
   297→
   298→Artifact name: `rollback-evidence-<github.run_id>`. Retention 90 days.
   299→
   300→### 6.4 Safety guards
   301→
   302→- `concurrency: { group: rollback-production, cancel-in-progress: false }` — never run two rollbacks concurrently.
   303→- `environment: production` — gives the GitHub environment reviewers one final chance to abort before the job runs.
   304→- `vercel promote` is **idempotent** — re-targeting the current production deployment to itself is a no-op.

   345→## 8. Supabase Connectivity Strategy (IPv6 / Pooler)
   346→
   347→### 8.1 The problem
   348→
   349→Supabase's direct connection string (`db.<project-ref>.supabase.co:5432`) resolves to **IPv6** in many regions. Vercel serverless functions egress **IPv4-only**. The result is `ECONNREFUSED` or `ENETUNREACH` at runtime — the kind of failure that only manifests after deployment (not in local dev where IPv6 may be available, and not in CI where the test DB is SQLite).
   350→
   351→### 8.2 The fix — use the Supabase **Transaction Pooler** (PgBouncer)
   352→
   353→```
   354→postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=1
   355→```
   356→
   357→| Property | Value | Reason |
   358→|---|---|---|
   359→| Host | `aws-0-<region>.pooler.supabase.com` | Supabase's PgBouncer pooler — IPv4-capable |
   360→| Port | `6543` | Transaction-mode pooler port |
   361→| `?pgbouncer=true` | — | Tells Prisma to use the pooler's transaction mode |
   362→| `?connection_limit=1` | — | Required for serverless — each function instance gets exactly one connection, preventing pool exhaustion |
   363→| Role | `snakzap_app` | Per DEV-001 — the WORM boundary REVOKE only protects the app if the app connects as snakzap_app. NEVER `postgres` superuser. |

   366→
   367→Prisma migrations **cannot run over PgBouncer transaction mode** (Prisma needs a session for DDL). The migration runner (the GitHub Action that runs `prisma migrate deploy`, or the `psql` invocation of `postgres-migration.sql`) must use:

   369→```
   370→DIRECT_URL=postgresql://postgres.<project-ref>:<admin-password>@aws-0-<region>.pooler.supabase.com:5432/postgres

   372→

   383→## 9. Vercel / Bun Compatibility Assessment
   384→
   385→### 9.1 What Vercel supports for Next.js
   386→
   387→- Vercel's Next.js builder (`@vercel/next`) uses the **Node.js runtime** (`nodejs20.x` / `nodejs22.x`) for both the build phase and the runtime phase (serverless functions + Edge runtime for middleware).
   388→- Vercel auto-detects Bun via the presence of `bun.lock` / `bun.lockb` in the project root and uses **Bun as the package manager** during install (`bun install --frozen-lockfile`).
   389→- Vercel does NOT run the Next.js app on the Bun runtime in production. The `bun` command is only used by Vercel during dependency installation. Build + serve both happen on Node.
   390→
   391→### 9.2 What the project does with Bun
   392→
   393→| Phase | Tool | Runs on |
   394→|---|---|---|
   395→| `bun install` | Bun | Bun (lockfile-driven) |
   396→| `bun run dev` | `next dev` | Node (Next.js dev server) |
   397→| `bun run build` | `next build` | Node (Next.js build) |
   398→| `bun run start` | `bun .next/standalone/server.js` | **Bun** runtime (only in the Docker image, not on Vercel) |
   399→| `bun run lint` | `eslint .` | Node (eslint binary) |
   400→
   401→The `start` script uses Bun as the production runtime — this only matters for the Dockerfile / long-lived hosts. On Vercel, the project never reaches the `start` script: Vercel's `vercel build` step runs `next build` and the resulting serverless functions are invoked on Vercel's Node runtime.
   402→
   403→### 9.3 Compatibility verdict
   404→
   405→✅ **Compatible.** No code change required.
   406→
   407→- `next.config.ts` declares `output: "standalone"`, which Vercel's Next.js builder respects (it can also use the standalone output, though Vercel's default builder does not require it).
   408→- The `package.json` `build` script is `next build && cp -r .next/static .next/standalone/.next/ && cp -r public .next/standalone/`. The `cp` commands target the standalone directory — Vercel ignores this directory because it builds its own bundle. The `next build` portion is what Vercel runs.
   409→- Prisma Client is generated by `bunx prisma generate` during Vercel's install phase (it has a `postinstall` hook from `@prisma/client`). The generated client works on Node runtime as well as Bun — Prisma Client is engine-agnostic (uses libquery_engine for both).
   410→- Socket.io is used in `mini-services/realtime` — NOT in the Next.js app. Vercel serverless functions don't hold WebSocket connections, but the Next.js app uses socket.io-client (server-side, in `src/lib/realtime.ts`) to emit events to the realtime mini-service. This works on Vercel — the Next.js API route makes an outbound socket.io-client connection to the separately-hosted realtime service (Fly.io). The `getSocket()` singleton pattern in `src/lib/realtime.ts:11` may need a refresh for serverless (each function invocation is a fresh process — the singleton only helps within one warm invocation). Documented as §12 follow-up.
   411→
   412→### 9.4 One known caveat — `realtime.ts` singleton
   413→
   414→```ts
   415→const globalForRealtime = globalThis as unknown as { __realtimeSocket?: Socket }
   416→function getSocket(): Socket | null {
   417→  if (globalForRealtime.__realtimeSocket) return globalForRealtime.__realtimeSocket
   418→  // ...
   419→}
   420→```
   421→
   422→On Vercel serverless, `globalThis` is per-invocation (not shared across warm starts reliably). Each invocation that calls `emitOrderUpdated` etc. opens a new socket.io-client connection. This is acceptable (socket.io-client connections are cheap) but introduces per-request latency. For Phase 2, this is fine — flag for future optimization if latency budget is exceeded.
