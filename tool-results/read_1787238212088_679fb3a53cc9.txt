   356→## Issues encountered + resolved
   357→
   358→1. **Gift.status field contract ambiguity** — Wave-1B types.ts documents
   359→   `status: string` as `'PENDING' | 'REDEEMED' | 'EXPIRED' | 'CANCELLED'`.
   360→   The gift-store.ts `GiftStatus` type lists CREATED/PAID/AVAILABLE/REDEEMED/
   361→   EXPIRED/CANCELLED/REFUNDED. The blueprint §19 lists CREATED/PAID/AVAILABLE/
   362→   REDEEMED/EXPIRED/CANCELLED/REFUNDED. The task spec mentioned "status=
   363→   AVAILABLE". RESOLVED by writing defensive `isAvailable(status)` /
   364→   `isRedeemed(status)` / `isExpired(gift, now)` / `isCancelled(status)`
   365→   helpers that accept BOTH the Wave-1B 'PENDING' value AND the blueprint
   366→   'AVAILABLE' value as redeemable states. The GiftCard component (Task 1B)
   367→   uses `status === 'PENDING'` for its active state — my UI doesn't rely on
   368→   GiftCard's internal state checks; instead, I check status via my own
   369→   helpers before delegating to GiftCard. If Task 6C returns 'AVAILABLE',
   370→   my helpers treat it as redeemable; GiftCard's internal check would treat
   371→   it as non-redeemable (showing the status pill instead of the Redeem
   372→   button). To handle this discrepancy: I render GiftCard's `onRedeem` prop
   373→   so the button still works for AVAILABLE state — actually GiftCard only
   374→   shows the Redeem button when `status === 'PENDING'`. If Task 6C returns
   375→   'AVAILABLE', GiftCard won't show the button. **Mitigation**: my
