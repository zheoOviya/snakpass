   196→### 7.1 P0 — Cannot Launch Without It
   197→
   198→The `Protects` column lists which Business Invariants (Section 9) the capability is responsible for upholding. A capability may not reach `Production-ready` until every invariant it protects is verified.
   199→
   200→**Capability classification (v1.4):** Every P0 is one of two types:
   201→- **Direct Protector** — a capability that *enforces* one or more business invariants directly (e.g. P0-01 enforces I-01 Payment Integrity by rejecting unsigned captures). Its `Protects` column lists specific I-xx IDs.
   202→- **Control/Enabler** — a capability that *detects, enables, or preserves* the system but does not enforce a specific business truth (e.g. P0-19 logging detects failures but does not enforce payment integrity; P0-15 migrations preserve schema but do not enforce any single invariant). Its `Protects` column reads `(Control/Enabler)`.
   203→
   204→This distinction matters for Coverage Query A (Section 18.5): a Direct Protector must map to ≥1 specific invariant; a Control/Enabler legitimately does not. Calling observability an "indirect protector of I-01" would distort the architecture — observability detects I-01 violations, it does not enforce them. The classification keeps ownership honest.
   205→
   206→**Architectural Law 6 (v1.4):** *An invariant describes a truth that must never be violated; a capability describes the mechanism that enforces or preserves that truth.* Direct Protectors enforce; Control/Enablers preserve the conditions under which Direct Protectors can function. Both are P0; their relationship to invariants differs.

   291→## 8. Detailed 5-Question Breakdowns (P0 + P1)
   292→
   293→Each capability below has all five questions answered. A capability is **not ready** until the corresponding test criteria pass.
   294→
   295→### P0-1 · Razorpay Payment Create + Verify + Capture
   296→
   297→1. **Happy Path:** Consumer places order → backend creates Razorpay order → Checkout SDK opens → user pays → `payment.success` → backend verifies signature → marks Payment CAPTURED → marks Order CONFIRMED → emits `ORDER_CONFIRMED` event.
   298→2. **Failure Path:**
   299→   - Gateway timeout during order create → rollback order to PAYMENT_PENDING; consumer sees retry.
   300→   - Signature mismatch → reject; do not capture; alert; consumer sees "payment failed, try again".
   301→   - Double Pay click → second request rejected via idempotency key; first proceeds.
   302→   - Webhook arrives before client callback → handle via webhook; client callback becomes no-op.
   303→   - Capture succeeds but DB write fails → reconciliation job finalises; consumer sees "processing" until reconciled.
   304→3. **Recovery Path:** Reconciliation job hourly; mismatches → exception queue; manual capture/refund via admin with audit.
   305→4. **Money / Trust Impact:** **Critical.** Captured-without-order = lost money. Failed-but-marked-paid = fulfilment of unpaid order = inventory loss. Both destroy trust instantly.
   306→5. **Observability:** Structured log per payment state transition; metric `payment_success_rate`; alert if < 95% over 5 min window; reconciliation report daily.
   307→
   308→### P0-2 · Payment Ledger (double-entry)
   309→
   310→1. **Happy Path:** On CAPTURED, ledger entries: `Dr. Gateway Receivable / Cr. Consumer Revenue`; on payout: `Dr. Vendor Payout / Cr. Gateway Receivable`; on refund: `Dr. Refund Expense / Cr. Gateway Payable`.
   311→2. **Failure Path:** Ledger write fails after capture → captured payment without ledger entry → reconciliation flags.
   312→3. **Recovery Path:** Reconciliation job detects missing entries; auto-creates from gateway record; audit logged.
   313→4. **Money / Trust Impact:** **Critical.** Ledger drift = untraceable money = compliance failure.
   314→5. **Observability:** Ledger integrity check hourly; alert on any imbalance.
   315→
   316→### P0-3 · Payment Reconciliation (gateway ↔ ledger)
   317→
   318→1. **Happy Path:** Hourly job fetches gateway settlements, compares to ledger; matches mark RECONCILED; mismatches go to exception queue.
   319→2. **Failure Path:** Job fails → last-run timestamp stale → alert; no silent skip.
   320→3. **Recovery Path:** Re-run job; manual reconciliation for edge cases.
   321→4. **Money / Trust Impact:** **Critical.** Unreconciled payments = unknown financial state.
   322→5. **Observability:** Reconciliation report dashboard; alert on mismatch count > 0 for > 1 hour.
   323→
   324→### P0-4 · Refund Flow
   325→
   326→1. **Happy Path:** Refund requested → REFUND_REQUESTED → Razorpay refund API → REFUND_PROCESSING → webhook → REFUNDED → ledger entry.
   327→2. **Failure Path:** Gateway down → REFUND_REQUESTED stays; retry queue; alert if stuck > 1 hour.
   328→3. **Recovery Path:** Manual refund via admin with audit; ledger corrected.
   329→4. **Money / Trust Impact:** **Critical.** Unprocessed refund = consumer money trapped = trust loss + legal exposure.
   330→5. **Observability:** Refund SLA metric; alert on REFUND_REQUESTED older than 1 hour.
   331→
   332→### P0-5 · Webhook Integrity
   333→
   334→1. **Happy Path:** Webhook arrives → HMAC verified → idempotency check → process → 200 OK.
   335→2. **Failure Path:** Tampered signature → 400 + alert; duplicate → dedup, 200 OK (idempotent); out-of-order → reorder by timestamp, process in order.
   336→3. **Recovery Path:** Reconciliation job catches anything webhooks missed.
   337→4. **Money / Trust Impact:** **Critical.** Forged webhook = fake capture = unpaid fulfilment.
   338→5. **Observability:** Webhook log; alert on signature failures.

   340→### P0-6 · Order State Separation
   341→
   342→1. **Happy Path:** Order, Payment, Fulfilment, Refund each have independent status; UI composes them.
   343→2. **Failure Path:** Inconsistent combo (e.g. Order CANCELLED + Payment CAPTURED) → exception queue entry; auto-refund triggered.
   344→3. **Recovery Path:** Exception queue drives manual or automated resolution.
   345→4. **Money / Trust Impact:** **Critical.** Inconsistent states = money leaks.
   346→5. **Observability:** Invariant checker hourly; alert on any inconsistent combo.

   348→### P0-7 · Order State Machine Hardening (v1.4 — pickup attribution expanded)
   349→
   350→1. **Happy Path:** Valid transitions only (CONFIRMED → PREPARING → ALMOST_READY → READY → PICKED_UP). The PICKED_UP transition is the highest-integrity transition in the system — it marks the handoff of food to the customer. As of v1.4, PICKED_UP is valid **only when all 8 attribution conditions hold**:
   351→   1. Correct `order_id` resolved and verified.
   352→   2. Authorized collector/customer identity verified.
   353→   3. Required QR + OTP verification succeeded (both, per I-13 + Q21).
   354→   4. Pickup event persisted with at minimum: `order_id`, collector identity/reference, timestamp, verification method/result, actor/source.
   355→   5. Pickup event written to the immutable audit trail (links to P0-22 evidence).
   356→   6. Duplicate pickup attempt idempotently rejected/handled (no double-PICKED_UP).
   357→   7. Cross-credential pickup impossible (one order's credential cannot pick up another order).
   358→   8. Attribution failure blocks the PICKED_UP transition and activates the exception/recovery path (does not silently mark picked up).
   359→2. **Failure Path:** Invalid transition → 409; concurrent update → optimistic lock rejects loser with retry guidance; pickup verification failure (any of conditions 1–3, 6, 7 fail) → transition blocked, order stays READY, exception path activates.
   360→3. **Recovery Path:** Manual override via admin with audit (for state-machine conflicts); for attribution failures, exception queue entry created per P0-28 blast-radius Level 1 (transaction freeze on the affected order) — human investigates, corrects, and re-attempts pickup.
   361→4. **Money / Trust Impact:** **High → Critical (v1.4).** Wrong state = wrong fulfilment. A PICKED_UP without verified attribution = food handed to the wrong person = direct consumer harm + trust destruction + potential refund liability. I-13 (Pickup/Handoff Integrity) is now fully owned by P0-07.
   362→5. **Observability:** Transition log; alert on invalid-transition attempts; **pickup-verification log** (per attempt: order_id, collector, method, result); alert on attribution-failure rate; P0-22 audit-trail linkage verified on every PICKED_UP.
   363→
   364→**Test criteria (v1.4 — expanded):**
   365→- Concurrency test (existing)
   366→- Invalid-transition test (existing)
   367→- **Pickup-verification: correct collector** — valid QR+OTP, correct order → PICKED_UP succeeds, audit event persisted with all 5 fields.
   368→- **Pickup-verification: wrong collector** — credential belongs to a different order/customer → transition blocked (condition 7), exception path activates.
   369→- **Pickup-verification: QR/OTP failure** — missing or mismatched QR or OTP → transition blocked (condition 3), clear error to operator.
   370→- **Pickup-verification: duplicate pickup** — second PICKED_UP attempt on already-picked order → idempotent reject (condition 6), no double-transition.
   371→- **Pickup-verification: attribution/audit persistence** — after a successful PICKED_UP, the audit event is present in P0-22's immutable trail with all 5 required fields; tamper attempt detected.
   372→
   373→**Evidence linkage (v1.4):** P0-07 enforces I-13 at the transition gate; the resulting pickup event flows to P0-22 (Audit Integrity) as immutable evidence. The relationship is: **P0-07 (mechanism) → I-13 (truth enforced) → P0-22 (evidence preserved)**. P0-07 is NOT renamed "Pickup Audit Attribution" — attribution is an integrity condition of the PICKED_UP transition, owned by the state-machine capability. P0-22 remains the audit-trail owner; P0-07 remains the transition owner.

   503→### P0-24 · Transactional Data Integrity (cross-entity) — idempotent business effect
   504→
   505→1. **Happy Path:** Order creation writes Order + OrderItems + decrements availability + writes outbox event atomically (single DB transaction). Payment capture updates Payment + Ledger + Order status atomically. The outbox publisher later delivers the event to notifications/analytics/settlement.
   506→2. **Failure Path:**
   507→   - **Partial failure mid-transaction** → entire business transaction rolls back; no orphan OrderItems, no orphan ledger entries, no decremented availability without an order.
   508→   - **Outbox publisher crashes after commit** → the event row is already committed in the DB (part of the same transaction), so it is NOT lost. Publisher restarts and re-publishes. Consumers may receive the event more than once → consumers must be idempotent, so the **business effect is exactly-once** even if physical delivery is at-least-once.
   509→   - **Consumer crashes mid-handling** → event re-delivered; idempotency key on consumer side ensures no double-application.
   510→3. **Recovery Path:** Outbox processor retries indefinitely with backoff; reconciliation job catches drift between transactional writes and emitted events; consumers dedup via idempotency key. The committed business transaction is never lost.
   511→4. **Money / Trust Impact:** **Critical.** This is the difference between "DB is consistent" and "the world the DB describes matches the world the rest of the system acted on." A captured payment without a delivered settlement event = vendor never paid = silent money leak.
