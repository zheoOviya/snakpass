## 1. Publisher PENDING → PUBLISHED/FAILED Semantics

### Design
The outbox publisher worker (`mini-services/outbox-publisher/`) polls the `Outbox` table for `status='PENDING'` rows, delivers each via Socket.io, and updates the row:

| Transition | Condition | Action |
|------------|-----------|--------|
| PENDING → PUBLISHED | Socket.io emit succeeds | Set `status='PUBLISHED'`, `publishedAt=now()` |
| PENDING → PENDING (retry) | Socket.io emit fails, attempts < max | Increment `attempts`, set `lastError`, keep PENDING |
| PENDING → FAILED | attempts >= max (5) | Set `status='FAILED'`, set `lastError` |
| PUBLISHED → (terminal) | — | No further processing |
| FAILED → (terminal) | — | Manual intervention required (alert fires) |

### Acceptance Evidence Required
- ✅ PENDING row becomes PUBLISHED after successful emit
- ✅ PENDING row stays PENDING after failed emit (attempts incremented)
- ✅ PENDING row becomes FAILED after 5 failed attempts

## 2. Retry + Crash Recovery

### Design
- **Retry schedule:** 1s, 5s, 30s, 5min, 15min (exponential backoff)
- **Max retries:** 5 (then status=FAILED)
- **Crash recovery:** If the publisher process crashes mid-publish, the outbox row remains PENDING (the UPDATE to PUBLISHED hasn't committed). On restart, the publisher re-reads PENDING rows and re-delivers.
- **At-least-once delivery:** The same event may be delivered more than once (if publisher crashes between emit + PUBLISHED update). Consumer-side dedup handles this.

### Acceptance Evidence Required
- ✅ Kill publisher mid-publish → restart → event re-delivered (no event lost)
- ✅ Event delivered at-least-once (may be >1 delivery; consumer dedup ensures exactly-once business effect)

## 3. Consumer-Side eventId Deduplication

### Design
Per Q17 decision: the `eventId` (UUID generated by `enqueueOutboxEvent`) is the consumer-side idempotency key.

New model: `ProcessedEvent`:
```
model ProcessedEvent {
  eventId     String   @id  // matches Outbox.eventId
  eventType   String
  processedAt DateTime @default(now())
}
```

Consumer flow:
1. Receive event (from Socket.io or other channel)
2. Check `ProcessedEvent` table for `eventId`
3. If exists → skip (already processed)
4. If not exists → apply business effect + INSERT ProcessedEvent (in same transaction)
5. If step 4 fails → event not marked processed → re-delivered on next publish

### Acceptance Evidence Required
- ✅ Same eventId delivered 3× → business effect applied exactly once
- ✅ ProcessedEvent row exists after first delivery

## 4. Duplicate Delivery → Business Effect Applied Once

### Design
This is the core of P0-24's "idempotent business effect" principle:
> "We do NOT chase technical 'exactly-once delivery.' We chase idempotent business effect."

The consumer (currently the realtime service, which emits to browser clients) must be idempotent:
- **Socket.io emit is already fire-and-forget** — browsers may receive duplicate events
- **Browser-side dedup:** The frontend already handles this implicitly (order status updates are idempotent — setting status to PREPARING twice has no additional effect)
- **For future consumers** (payment webhook handler, etc.): use ProcessedEvent table

### Acceptance Evidence Required
- ✅ 3× delivery of same event → 1× business effect (verified via ProcessedEvent table)

---

## 5. Poison Event / Permanent Failure Handling

### Design
If an event cannot be delivered after max retries (5):
- Status → FAILED
- `lastError` set to the final error message
- Alert fires: `outbox-publish-failed`
- Manual intervention required (admin investigates + re-queues or discards)

**No infinite retry.** A poison event stops the publisher from retrying that specific event but doesn't block other events.

### Acceptance Evidence Required
- ✅ Event fails 5× → status=FAILED + alert fires
- ✅ Other events continue to be processed (no blocking)

## 6. Outbox Lag Measurement + Alert

### Design
- **Metric:** `outbox_lag_seconds` = age of oldest PENDING outbox row (`now() - createdAt`)
- **Alert rule:** `outbox-lag-exceeded` — fires when lag > 60 seconds (configurable)
- **Alert severity:** `warning` (not critical — events are persisted, just delayed)
- **If lag > 5 minutes:** escalate to `critical` (possible publisher crash)

New alert rule to add to `src/lib/alerting.ts`:
```
{
  id: 'outbox-lag-exceeded',
  name: 'Outbox Lag Exceeded',
  description: 'Oldest unpublished outbox row > 60 seconds old',
  severity: 'warning',
  metric: 'outbox_lag_seconds',
  threshold: 60,
  comparison: 'gt',
  cooldownMs: 60_000,
}
```

### Acceptance Evidence Required
- ✅ Outbox lag metric produced when publisher is running
- ✅ Alert fires when lag exceeds threshold (simulated by stopping publisher)

## 7. Production Safety of /api/test/rollback-injection

### Orchestrator Concern
> "VERCEL_ENV guard बदलना अपने-आप production safety का पर्याप्त प्रमाण नहीं है; production में route वास्तव में unavailable है, इसका explicit evidence चाहिए।"

### Design — Explicit Production Unavailability Evidence
The test endpoint must be provably inaccessible in production. The VERCEL_ENV guard is the first line of defense, but additional evidence is required:

1. **Code-level guard:** `if (process.env.VERCEL_ENV === 'production') return 403`
2. **Vercel route config:** Add to `vercel.json` a route-specific header or redirect that blocks `/api/test/*` in production
3. **Staging-only verification workflow:** `subwave-2a-rollback-evidence.yml` verifies the endpoint works on staging (VERCEL_ENV=preview)
4. **Production unavailability test:** A new workflow that hits the production URL (if it exists) and verifies it returns 403/404

### Acceptance Evidence Required
- ✅ Staging (VERCEL_ENV=preview): endpoint returns 200 with testMarker (already verified)
- ✅ Production (VERCEL_ENV=production): endpoint returns 403 (requires production deployment — NOT authorized yet)
- **Mitigation:** Since production deployment is NOT authorized, the endpoint cannot be accessed in production. The VERCEL_ENV guard is a code-level safety net for when production deployment eventually happens.

- Create `src/lib/event-consumer.ts` — `processEvent(eventId, eventType, handler)` that:

  - If not processed: runs handler + inserts ProcessedEvent (in same transaction)
  - If already processed: skips (dedup)

- Add `outbox-lag-exceeded` alert rule to `src/lib/alerting.ts`
- Add `outbox-publish-failed` alert rule for FAILED events
